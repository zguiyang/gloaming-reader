# Gloaming — Library IA V2 / 产品交互方案

**状态：待产品审查；未批准实施**
**范围：Library、Tags、Book Detail 信息架构与交互，不涉及业务代码或数据库变更。**

> 文中“当前事实”来自当前 `dev-02` 源码及上一轮 `library-ia-audit.md`；“推荐”是本轮方案，等待用户和 ChatGPT 审查。方案不能自动改变 `docs/product/prototype-flows.md` 等已确认的产品流程。

## 1. 设计目标

1. **不要求用户理解内部模型。** 页面只使用“全部书籍、我的上传、已保存、阅读中、标签”等用户熟悉的语言；不向用户暴露 ReadingWork、SourceRecord、Membership 或 Catalog。
2. **低认知负担，常用动作就近可见。** 找书与切分类直接呈现；继续阅读有明显快捷入口；标签创建、修改和删除放在用户需要时才展开的控件中。
3. **一个书库，多种轻量组织方式。** 来源说明“这本书从哪里来”，私有标签说明“我如何整理它”；两者可组合筛选，但不再造文件夹、Collections 或多层分类。
4. **阅读入口始终清楚。** 书籍信息查看与继续阅读是两个明确动作；阅读状态和书籍是否已在书库分别展示，不能相互推断。
5. **跨设备保持位置感。** 当前分类、搜索和筛选可恢复；移动端把侧栏收进一个明确的分类入口，不牺牲书籍内容空间。

## 2. 推荐信息架构

### 2.1 三个界面的职责

| 界面                       | 用户来这里做什么                            | 主要内容与动作                                                                                     |
| -------------------------- | ------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| **Library / 书库**         | 找到、查看、阅读和整理已有书籍              | 桌面左侧来源/标签导航；右侧继续阅读、搜索和阅读状态筛选、排序与展示方式、统一书籍列表              |
| **Tags / 标签管理**        | 管理标签本身                                | 新建、重命名、删除、查看关联书数；点标签名/书数进入书库并选中该标签                                |
| **Book Detail / 书籍详情** | 了解一本书，再决定开始/继续读或管理个人书籍 | 标题、作者、封面、描述、来源、阅读状态/进度、章节目录、阅读 CTA；个人书籍的元数据/标签管理按需出现 |

书库是日常起点。标签不是另一套书架，详情也不是 Discover 的子页面。Discovery 来源记录仍是独立对象和后续独立功能，不在本轮设计 SourceRecord 前端。

**产品 SSOT 冲突，需在批准时一并解决**：`docs/product/prototype-flows.md` §4 将“我的书架 / Open shelf item → Reader”和“发现 / Open item → Reader”标为 Confirmed；`docs/product/mvp-1-modules.md` §3、§4.3–4.4 也以打开阅读直达 Reader 为主路径。`prototype-flows.md` 顶部同时记录 `/discover/[workId]` 为 detail 路由，因此“详情存在”不等于“书卡必须先经过详情”。本设计推荐卡片封面/标题打开详情、显式阅读 CTA 直达 Reader，是有意提出的新产品流程，必须在用户批准后更新流程 SSOT；当前 Library 测试也显式要求没有 `/discover/` 书卡链接（`apps/web/features/library/library-page.spec.ts:191-196`）。

**名称冲突**：`mvp-1-modules.md:80,85` 锁定“我的书架”作为用户可见名称；当前 Web 导航文案是“书库”。本设计线框暂用当前界面的“书库”便于对应现状，批准实施前需要选定并同步 SSOT 与 i18n；它与侧栏布局决定相互独立。

**当前入口事实**：Library 卡片与 History 条目主点击都进入 Reader；History 没有详情次级入口。Reader 的 TOC 有详情链接，但当前是裸 `/discover/:workId`；Reader 返回在缺少浏览器历史时 fallback 到 Discover。详情页仅移动端显示固定“返回发现”，没有 Library/History/Reader 来源语境。V2 的返回契约是建议目标，不是当前行为。

### 2.2 Library 桌面导航组织

**推荐：桌面采用左侧组织导航 + 右侧统一内容区。** 这比继续把所有来源和标签堆在顶部更适合标签数量增长，也能让用户在任一筛选状态下看到自己身处哪一类。来源与用户标签是同一列表的两个筛选维度，而不是彼此嵌套的书架。

侧栏是 Library 页面内部的组织方式，不增加一个新的一级目的地；搜索留在当前页面工具栏，不单独增加 Search 页面。这符合 `mvp-1-modules.md` 将布局留给原型、但限定一级模块集合的边界。

侧栏分为两个有标题的平面分组，不设置子分类树：

- **来源**：全部书籍、我的上传、已保存。当前项有明确选中态与结果标题。
- **我的标签**：每个标签一行，右侧显示关联书数；顶部右侧设置图标进标签管理；底部 `+ 新建标签`。
- 标签按名称排序；标签多时该分组可滚动，不折叠为二级目录。当前选中标签保持可见或由列表滚至选中项。
- 来源数量只有在后端提供全量准确计数后才展示；不能从当前最多 48 条的响应推算总数。wireframe 中来源数量仅为结构示例。标签关联数使用现有全量标签计数。
- 侧栏 `+ 新建标签` 展开一个小型行内输入；保存后新增标签显示为 0 本，留在原筛选，不自动切入空结果。若用户从某本书的管理菜单新建，则创建后立即关联该书。

右侧内容区只显示当前来源/标签所选书籍的结果。标签和来源条件组合取交集：例如“我的上传 + 科幻”只显示同时满足两个条件的书。`全部书籍` 相当于不限制来源；选中的标签仍可叠加。标签选择可一键取消或点击“全部标签”。

### 2.3 右侧工具区层级

不把每个功能都做成常驻大控件。推荐分层：

1. 标题行：当前来源/标签名称、结果数量，以及有活动条件时的“清除筛选”。
2. 紧凑工具栏：一个主要搜索框；阅读状态、排序、网格/列表使用紧凑控件。
3. 结果区域：书籍卡片/列表。每张书以标题/作者/封面进入详情，阅读 CTA 单独显式进入 Reader，更多菜单放低频管理动作。

工具栏状态：

- 搜索范围始终是当前来源和标签结果；例如先选“我的上传”再搜，搜索不会跳出当前分类。
- 状态筛选：全部、未开始、阅读中、已完成。它基于真实 `ReadingState.status`，不以 0% 推断未开始。
- 排序第一版只提供最近活动/最近加入、标题。若后端没有可靠的“最近加入”字段，应在接口定义完成后再决定默认项，不用 UI 假造。
- 网格/列表切换属于展示偏好，不改变当前筛选结果。可记在本地偏好；筛选、搜索和排序则进入 URL。
- “清除筛选”清除来源、标签、阅读状态和搜索；回到“全部书籍”默认状态。当前列表标题仍显示当前作用范围，避免用户忘记筛选状态。

### 2.4 继续阅读的位置与重复卡片

**推荐放在右侧内容区标题之下、工具栏之上，作为窄幅的“继续阅读”快捷条。** 它只在存在可继续作品时出现，呈现书名、当前章节/进度和“继续阅读”按钮。点击直接进 Reader，不进入详情。

继续阅读是用户回到阅读的快捷操作，不是来源/标签筛选结果，所以切换左侧导航不应令它消失。它可能与下方 All Books 结果中的同一本书重复；这是两个不同任务的重复入口，可以接受，但需用紧凑样式与“继续阅读”标签区别，不再重复一个大封面 Hero。若某本完成了，不出现在 Continue Reading；仍留在书格并由“已完成”筛选访问。

### 2.5 空状态、单本书与大书库

- **没有标签**：侧栏仍展示“我的标签”，用一句简短说明标签可用于整理书籍，并提供 `+ 新建标签`。不要先将用户送去空的管理页。管理页也保留同一创建入口。
- **没有书**：右侧展示友好的空书库状态和明确的“上传 EPUB”/“去发现”入口（具体可用性按当前产品能力显示），左侧结构保留，让新用户知道以后书籍会在哪里。
- **筛选无结果**：保留当前分类标题，说明“没有符合条件的书”，提供清除搜索与条件动作；不要将其误显示为“书库为空”。
- **只有一本书**：正常显示一个完整书卡/列表行；继续阅读条（如果在读）可作为快捷入口，不需要铺满大型空白或假造推荐内容。
- **上百本书**：桌面侧栏仍一层，不增加树形层级；标签列表可纵向滚动。右侧搜索按当前分类工作，结果采用稳定排序和分页/加载更多。需要 API 在数据库查询层先应用 source/tag/status/search/sort，再做 cursor 分页；只在已拿到的前 48 条里过滤会漏书。

## 5. Interaction Contract

| 用户操作                 | 触发位置                              | 实际动作                                                              | 目标页面/结果                          | 返回行为                                                      | 状态保留行为                                            |
| ------------------------ | ------------------------------------- | --------------------------------------------------------------------- | -------------------------------------- | ------------------------------------------------------------- | ------------------------------------------------------- |
| 点击书籍封面/标题        | Library 网格/列表卡片                 | 打开该 Work 的详情；不自动改变阅读进度                                | Book Detail                            | 返回触发它的书库列表                                          | 保留 source、tag、search、status、sort、view 及滚动位置 |

### 路由与返回建议

**推荐的用户概念路由**：Work 详情归于通用书籍/作品路由（如 `/works/[workId]`），而不是产品概念上归于 Discover。现有 `/discover/[workId]` 作为旧链接兼容入口，重定向到规范 Work Detail，保留合法的返回语境。

返回上下文由应用内链接显式传递相对站内 `returnTo`（包含 library query）并校验为本站允许的路径。详情 Header 返回按钮使用这个语境；若无语境则 fallback 到 Library。浏览器 back 可作为增强，但不能作为刷新后唯一可用路径。

- Library → Detail：`returnTo=/library?...`。
- History → Detail：`returnTo=/reading-history`。
- Reader → Detail：`returnTo=/read/<workId>?part=...`，Reader 状态不因查看详情而重置。
- 直接链接/刷新：带有效 returnTo 时使用它；无 returnTo 时回 Library。

- `apps/web/features/library/library-tags-page.tsx`：增加到指定标签筛选书格的直接入口，保持标签 CRUD 单一所有权。
- `apps/web/features/book-detail/**`：呈现统一 Work 详情；阅读状态映射修正；按个人作品显示元数据和标签管理；回退语境及章节 Reader 链接。
- `apps/web/features/history/**`：加入次级详情入口，主阅读操作仍直达 Reader。
- `apps/web/features/reader/**`：确认详情入口携带 Reader 回访上下文。
- route modules：新增规范 Work Detail route，并处理旧 `/discover/[workId]` deep link。

最终文件归属要在实施时依据仓库现状复核；本设计不要求创建新的全局组件域或重排整个 Feature 目录。

### 路由

**需要**：为 Work Detail 建立与 Discover 无关的用户概念路由；保留旧深链转发；所有 `ReadingWork`/Work ID 链接使用一致 helper。SourceRecord 前端暂缓，不能用通用 ID 判别实体。

### API

**Phase 1–3 可以尽量复用**现有 Work、Library、ReadingState 和 User Tag API。详情状态映射属于 Web 客户端派生，不需要状态写入接口。

**Phase 4 需要 API 调整**：当前 Library Shared DTO/API 有 48 条限制，无法支撑完整搜索、状态筛选和稳定分页。建议让同一个 Library 查询 API 接受 source、tag、status、search、sort、cursor/pageSize；在数据库完整候选集上过滤排序后分页，并返回可继续取数的游标与必要计数。Continue Reading 保持独立返回，不应被这些条件过滤。

当前 Source/Tag 计数若仅针对返回的 48 条会误导。侧栏计数要么来自全量 facet counts API，要么在尚未支持时暂时不显示数值；不要把当前页数冒充总数。User Tag bookCount 已有标签级数据，可以继续显示。

### 数据库

**不需要数据库修改。** 现有私有 User Tag 与关联结构可以支撑侧栏导航、单标签筛选和书籍管理。分页、路由、状态呈现和偏好均可通过前端与现有/扩展查询 DTO 完成。不得增加 Collections、文件夹或 AI 标签 Schema。

## 8. Implementation Plan（各阶段独立验收）

### Phase 1 — IA-01 状态修复 + Book Detail 入口/导航

**范围**：修正 `in_progress + 0%` 状态显示；得到批准后让书卡封面/标题进入 Work Detail，显式 CTA 仍进 Reader；规范 Work Detail URL，旧 Discover deep link 兼容；详情返回 Library/History/Reader 上下文；章节 CTA 打开指定 part。

**真实用户验收**：

- Miss Moppet 状态为 `in_progress, 0%` 时 Library、History、Detail 都表达“阅读中/继续阅读”；0% 仍准确展示为 0%。
- 从 Library 与 History 点封面/标题进入详情，返回后筛选和滚动位置仍可找回；点 CTA 一步到 Reader。
- 从 Reader 打开详情再返回，章节和章内位置保持；刷新直达详情不出现死链，返回按钮有 fallback。
- Personal Work 显示自己的管理入口；Catalog Work 不出现编辑/删除个人元数据；“已在书库”与阅读状态同时可辨。

### Phase 2 — Library 页面布局与分类交互

**范围**：桌面左侧来源+标签导航、右侧主内容区；移动端分类抽屉；URL 中的 source/tag；Continue Reading 独立快捷条；当前分类标题与清除动作。阅读状态筛选、搜索、排序和视图切换放在 Phase 4。

**真实用户验收**：

- 用户能不用教程切换全部/上传/已保存；当前分类始终明显。
- 在“我的上传”选一个标签，结果只包含同时符合两条件的作品；清除后回到全部。
- 桌面窄窗口/390px 手机都能完整打开分类导航、选择后关闭并看到新结果。
- 刷新、浏览器前进/后退能恢复 source/tag 条件；继续阅读仍可见且不被标签过滤误隐藏。
- 只有一本书、没有书、过滤为空三种情况各自有合适的内容提示。

### Phase 3 — Tags 区域与管理闭环

**范围**：侧栏标签名和数量、创建入口、设置入口；Tags 管理页的查看书籍跳转；单书标签仍通过卡片/详情管理菜单关联或取消关联。

**真实用户验收**：

- 新用户从侧栏即可理解“标签用于整理”，无需先进入空白设置页才知道如何创建。
- 从单书菜单创建并关联标签后，侧栏出现该标签及正确书数；选择它立即筛出这本书。
- 从标签管理页的“查看书籍”到达带 tag 选择的 Library；rename 后关联不丢，delete 有确认且只删除标签关联。
- Personal 与 Saved Catalog Works 均能按当前用户标签筛选；另一用户看不到这些私有标签。

### Phase 4 — 搜索、排序、列表和必要分页

**范围**：稳定排序、搜索、阅读状态筛选、网格/列表偏好；API 先过滤再分页；来源/标签/状态计数按全量候选集计算或暂不展示。

**真实用户验收**：

- 1 本、48 本以上、100+ 本书库中，搜索、来源、标签、阅读状态可组合且不漏掉第 48 条以外匹配书。
- 搜索、状态、排序和网格/列表切换不改变筛选语义；分页/加载更多不重复、不漏书，翻页顺序稳定。
- Continue Reading 与分页结果相互独立；用户可以搜索出正在读的书并查看其当前状态。
- 手机工具区不会出现多行拥挤控件；低频排序/视图可按需展开但保持可发现。
